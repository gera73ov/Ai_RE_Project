# Трекер: агент сам передвигает задачи по колонкам (пример — YouGile)

**Агент обязан сам передвигать задачу в трекере по колонкам по мере работы.**
Ручное передвижение владельцем не предусмотрено; задача, «зависшая» не в той колонке, —
сбой агента.

> Это платформо-независимый слой правил (`.agents/rules/`): его читают агенты,
> начинающие работу в любом харнессе — OpenCode, Codex и другие. Харнесс-специфичные
> зеркала — `.claude/rules/tasktracker.md`, `.codex/rules/tasktracker.md`, раздел в корневом
> `AGENTS.md` до программ других харнессов. Правку канона делаешь здесь и зеркалишь.

## Колонки и статусы

Названия и состав колонок задаются при старте проекта; ниже — типовая схема на примере
YouGile. Адаптация под другой трекер: Linear — циклы/статусы, Jira — переходы статусов
и описание задачи; механика движения та же.

| Колонка | Когда |
|---|---|
| Backlog | задача в плане, работа не началась |
| In Progress | работа реально началась |
| In Review | реализация завершена, ждёт проверки |
| Done | критерии приёмки выполнены и приняты |

## Когда в какую колонку

1. **In Progress** — в момент, когда агент взял задачу и начал хоть что-то делать
   (первое чтение проблемы, планов, кода). Вызов MCP трекера (на примере `yougile`:
   `tools.yougile.manage_tasks` с существующим `id` задачи и `columnId` целевой колонки;
   `color: "primary"` — перечень цветов обязателен даже при простом переносе).
2. **In Review** — код готов, локальный QA-гейт прошёл (у каждого проекта свой набор:
   линтеры, тесты, audit секретов), описание задачи обновлено (что сделано / что осталось).
   Это сигнал QA-агенту.
3. **Done** — только после Pass от QA (или приёмки владельцем для задач без QA).
   Не переносить в Done самовольно, если критерии приёмки не выполнены.
4. Заблокировано извне — вернуть обратно в Backlog с короткой причиной в
   комментарии задачи (`tools.yougile.send_chat_message` — на примере YouGile).

## Ограничения

- Одновременно **не более одной** задачи в In Progress на одного агента: владелец
  всегда должен видеть, что «сейчас в работе».
- В In Review не копить больше 5; выросшую очередь разобрать (QA/принятие) и
  вернуть реальное состояние.
- На смене In Progress → In Review обновлять описание задачи (что сделано /
  что осталось) — трекер должен отражать реальность.
- Стикеры/метки/приоритет не менять без поручения владельца.

## Как (пример — MCP yougile)

- Прочитать: `tools.yougile.get_task_data({ id: "<chapter>-N", cursor: "" })`.
- Перенести/обновить: `tools.yougile.manage_tasks({ tasks: [{ id, title: null,
  columnId, description: null, color: "primary", complete: null, archived: null }] })`.
- Не блокирующие уточнения — комментарий в задаче, не чат владельцу.

## Ворота и DoD слоя 2 (product_docs — см. `product_docs.md`)

1. **Ворота.** Задачи Dev/QA не берутся в работу без пройденных ворот аналитики:
   карточка БФ в статусе `planned` (`product_docs/01_business_functions/BF-NN_*/README.md`)
   + утверждённые требования (пакет 5.5) + запись в трекере. Ворота не пройдены —
   назови причину и верни задачу аналитику; спецификацию сам не правь.
2. **Задачи привязываются к слою 2.** Задача ссылается на `BF-NN`, ID требований
   (FR-041, UC-ROS, …) и страницы компонентов, а не на файлы `output/reports/`.
3. **DoD перед Done.** Задача, меняющая требования или поведение, не переводится
   в Done, пока слой 2 синхронизирован: обновлены карточка БФ, страница компонента
   (`02_system_components/…`), строка `INDEX.md`, и `python product_docs/check_product_docs.py`
   выполняется без ошибок. Синхронизацию делает **аналитик** — Dev/QA/DevOps
   документацию не правят, а описывают изменение поведения комментарием к задаче.

## Эпики: задачи ↔ бизнес-функции

1. **Эпик = бизнес-функция.** Когда БФ проходит Гейт 2 (пакет 5.5 принят, карточка BF-NN в
   `planned`), создаётся задача-эпик вида «BF-NN: <название>». Все задачи функции (BA, Arch,
   UX, Dev, QA, DevOps, задачи системного анализа/интеграций) — подзадачи этого эпика.
2. **До появления БФ.** Работы BA ведутся в эпиках аналитики: стартовая фаза проекта —
   «Аналитика: <объём>», новая функция в живом проекте — в отдельном эпике «BF-NN: аналитика»
   (создаётся раньше BF-карточки). Работы без БФ (инфраструктура/ops) — эпик
   «Инфраструктура/ops».
3. **Связи.** Задачи ссылаются на BF-NN и ID требований; в карточке BF-NN хранится перечень
   задач эпика — обновляет **аналитик** при синхронизации слоя 2 (Arch создаёт задачи в
   трекере, но редактирует только трекер, не карточку).
4. **Эпик не двигается за подзадачами.** Он переходит: `In Progress` — при старте первой
   подзадачи; `Done` — когда все подзадачи Done и приняты (DoD слоя 2 закрыт).
5. **CR внутри эпика.** Если CR открыт, пока эпик не закрыт, — задачи CR посещают тот же
   эпик; эпик нельзя переводить в Done, пока CR-задачи не закрыты.
6. **CR-эпик после Done.** Для реализованной БФ будущие CR оформляются новым эпиком
   «BF-NN (CR-NNN)» (крупное изменение — «BF-NN v2»); цепочка BA→Dev→QA повторяется;
   документация ведётся в той же карточке BF-NN (растут версии).
7. **Название задач.** Единый формат: «[BF-NN] Pre.Dev-NN: <роль/тип — суть>»
   (для CR-эпиков — «[BF-NN / CR-NNN] …»). Формат читается одинаково в любом трекере.
8. **Адаптация к трекеру.** Правила описаны на примере YouGile (задача-эпик + подзадачи);
   в других трекерах — эпик/фича/milestone с привязанными задачами, механика та же.
